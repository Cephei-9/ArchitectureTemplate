\# CODE\_STYLE.md



\## 1. Общие правила


- Для каждого класса, структуры, енама и т.д. нужно писать summary. Но не писать комментарии внутри классов, структур и енамов

\- Не использовать `#region`.

\- Не использовать expression-bodied members (стрелочные методы и свойства).

\- Не использовать `var`. Всегда явно указывать тип переменной.

\- Не писать логику на одной строке после `if`.



---



\## 3. Именование



\### Приватные поля



\- `\_camelCase`

\- Обязательно с нижним подчёркиванием



Примеры:



```csharp

private int \_count;

private Vector2Int \_cellPosition;

```



\### Публичные поля и свойства



\- `PascalCase`



Примеры:



```csharp

public int CurrentIndex;

public bool IsActive { get; private set; }

```



---



\## 4. Unity и сериализация



\- Для настройки в инспекторе использовать `\[SerializeField] private`

\- Не использовать `public` поля для инспектора

\- Стараться не использовать константы, если значение можно вынести в инспектор



Стиль записи:



```csharp

\[SerializeField] private Vector2Int \_cellPosition;

\[SerializeField] private Button \_button;

\[SerializeField] private Image \_iconImage;

\[SerializeField] private Sprite \_xSprite;

\[SerializeField] private Sprite \_oSprite;

```



\### Важно



\- `\[SerializeField]` поля должны идти выше публичных полей.



---



\## 5. Порядок членов класса



Соблюдать следующий порядок (Microsoft-style):



1\. Константы

2\. Статические поля

3\. Публичные поля

4\. Приватные поля (включая `\[SerializeField] private`)

5\. Конструктор

6\. События

7\. Публичные свойства

8\. Приватные свойства

9\. Публичные методы

10\. Приватные методы

11\. Внутренние классы (nested) — внизу родительского класса



---



\## 6. Внутренние классы



\- Внутренние (nested) классы должны располагаться внизу родительского класса.


# Еще правила codestyle:


1. Нужно логировать важные точки реаботы приложения. Нужно логировать так, чтобы по логу можно было читать ход работы приложения
    - [ ]  Переходы из разных состояний игры
    - [ ]  Начало или завершение важных частей приложения
    - [ ]  Логировать ошибки если они случаются
2. Писать лог в такой нотации:
    
    `Debug.Log("[ClassName] Message.");`
    
    Пример: `Debug.Log("[GameInitialization] Game initialization completed successfully.");`
    
3. Делать new без типа
    - [ ]  Не правильно: `CancellationTokenSource cts = new CancellationTokenSource();`
    - [ ]  Правильно: `CancellationTokenSource cts = new();`
4. Не писать лог полной записью. Делать using UnityEngine; и укороченную запись: `Debug.Log("[Initialization] Game initialization completed successfully.");`
5. Если контент if блока занимает одну строку, то не нужно ставить скобки:
    - [ ]  Не прваильно:
        
        ```jsx
        if (success)
                    {
                        UnityEngine.Debug.Log("[Initialization] Game initialization completed successfully.");
                    }
                    else
                    {
                        UnityEngine.Debug.LogError("[Initialization] Game initialization failed.");
                    }
                    
        ```
        
    - [ ]  Не прваильно:
        
        ```jsx
                    if (success)
                        UnityEngine.Debug.Log("[Initialization] Game initialization completed successfully.");
                    else
                        UnityEngine.Debug.LogError("[Initialization] Game initialization failed.");
        
                    
        ```
        
6. Не писать комментарии внутри классов и функций. Комментарии нужно только чтобы описывать классы, структуры и енамы
7. Не нужно писать комментарии для внутренних классов, структур и енамов
8. Писать комментарии на английском языке
9. Не писать sealed для классов и структур. Это излишне
10. Писать скобки в пустых методах таким образом: 
`public override void InstallBindings() { }`
11. Ставить пустые строки между группами полей, свойств и методов:
    
    Пример:
    
    ```jsx
            public ReactiveProperty<float> Progress = new(0f);
	    public int SomeField;

            public int I { get; private set; }
	    public int SomeProp { get; set; }
    
            public void Dispose()
            {
                CurrentStepName.Dispose();
                Progress.Dispose();
            }
    ```
    
12. Стараться меньше проверять на null, и допускать аварийное завершение при наличии null. В большинстве случаев нужно предполагать что объект который тебе передают не пустой
    
    Вот здесь мы видим черезмерные проверки:
    `float totalWeight = _model.Steps.Sum(step => step == null ? 0f : Mathf.Max(0f, step.Weight))`
    
13. Использовать expression body у свойств если это возможно. Не использовать expression body у методов
14. Нужно добавлять постфикс к коллекциям:
    - [ ]  _someList; _someArr; _someMap(For Dictionarry), _someHashSet; и так далее
15. Для CancelationToken когда он парраметр в асинхронном методе нужно писать default
    - [ ]  Пример: `public UniTask<bool> RunAsync(CancellationToken cancellationToken = default)`

# Архитектура приложения: Policy / Application / View



Это архитектура \*\*приложения\*\*, а не геймплея.



Сюда входят: инициализация, главное меню, попапы, переходы между сценами, выход из игры и т.д.



\## Слои



\### 1) Policy (политики / правила)



\*\*Что это:\*\* чистая бизнес-логика, описывающая правила и ограничения.



\*\*Задача:\*\* принимать входные данные → возвращать решение/результат, без побочных эффектов.



\*\*Характеристики:\*\*



\- не зависит от Unity и UI

\- не вызывает платформенные SDK напрямую

\- хранит и обновляет своё состояние (если нужно) детерминированно

\- предоставляет интерфейс/контракт, через который Application использует правила



\*\*Примеры правил:\*\*



\- “нельзя показывать рекламу чаще чем раз в минуту”

\- “interstitial нельзя 2 минуты после rewarded”

\- “попап показываем только если выполнены условия”



---



\### 2) Application (логика приложения / флоу)



\*\*Что это:\*\* слой, который управляет тем, \*\*как работает приложение\*\*.



\*\*Задача:\*\* оркестрировать порядок действий и связывать всё вместе: политики, инфраструктуру, навигацию.



\*\*Содержит:\*\*



\- контроллеры/оркестраторы флоу (например MainMenuFlow, StartupFlow)

\- последовательности шагов (pipeline), чтобы порядок был явным

\- логику переходов между сценами

\- логику выхода из игры

\- обращение к платформенным реализациям через абстракции (адаптеры/интерфейсы)



\*\*Важно:\*\*



\- Application не рисует UI и не решает “как выглядят элементы”

\- Application определяет \*когда и что должно произойти\*, а View только отображает



---



\### 3) View (UI)



\*\*Что это:\*\* слой, который управляет тем, \*\*как отображать\*\* различные штуки.



\*\*Задача:\*\* показывать экраны/попапы/анимации и преобразовывать пользовательский ввод в вызовы Application.



\*\*Характеристики:\*\*



\- работает с Unity UI, анимациями, визуальными состояниями

\- подписывается на состояние/события из Application и отрисовывает

\- не содержит бизнес-правил и не принимает решения уровня Policy



---



\## Направление зависимостей (важное правило)



\- Policy ни от кого не зависит (в рамках этой архитектуры).

\- Application зависит от Policy и использует её как “правила”.

\- View зависит от Application: вызывает команды и отображает состояние.



Коротко: \*\*Policy → (используется) Application → (используется) View\*\*.



\## Геймплей



Геймплейная архитектура и игровой домен в этот документ не входят и описываются отдельно.
